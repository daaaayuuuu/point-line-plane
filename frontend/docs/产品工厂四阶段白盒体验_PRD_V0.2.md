| 项目 | 内容 |

## 2. 产品定义

点线面不是一个面向程序员的编码工具，而是一座面向非技术创造者的“产品工厂”。

用户只需要：

1. 说清楚想做什么；
2. 确认产品方案是否符合预期；
3. 在真实预览中体验并提出修改；
4. 确认发布，拿到可以使用和传播的产品。

需求分析、任务拆分、代码生成、模型调用、测试、版本管理、部署执行和运行监控由工厂在后台完成。

### 2.1 与 Codex 类产品的差异

| 维度 | Codex 类编码工具 | 点线面产品工厂 |
| --- | --- | --- |
| 核心用户 | 开发者或能参与技术协作的人 | 不懂技术的产品创造者 |
| 用户输入 | 代码任务、技术要求、仓库上下文 | 一个想法、业务目标或现有 PRD |
| 用户主要工作 | 审查代码、运行命令、处理技术问题 | 确认范围、体验、成本、风险和发布结果 |
| 过程展示 | 文件、代码、终端、日志、工具调用 | 产品方案、产品进度、真实预览、待确认事项 |
| 最终价值 | 完成开发任务 | 交付可体验、可上线、可继续运营的产品 |

产品差异化不在于“隐藏所有技术”，而在于把技术转换成用户能够判断的产品语言。

## 3. 核心产品模型

### 3.1 白盒与黑盒

产品内部保留完整的八阶段生产能力，但普通用户只看到四个白盒阶段。

| 白盒：用户需要理解和决定 | 黑盒：工厂负责完成 |
| --- | --- |
| 产品要解决谁的什么问题 | 需求结构化、上下文构建 |
| 核心功能与使用流程 | 任务拆分、依赖编排 |
| 技术方案带来的体验、成本和限制 | 框架选型、数据库设计、API 设计 |
| AI 在哪里工作、失败时怎么办 | 模型路由、提示词、Token 管理 |
| 需要提供哪些账号、数据和权限 | 密钥管理、运行环境配置 |
| 当前完成了什么、接下来发生什么 | 代码生成、测试执行、日志与重试 |
| 预览是否满意、哪里需要修改 | Git、构建、发布与回滚流程 |
| 上线地址、费用、风险和交付物 | 监控、告警、备份和运行维护 |

普通用户界面不提供“白盒/黑盒切换”。技术证据仅在二级入口“实现说明”中按需查看，用于排障、交接或专业人员审计。

### 3.2 四阶段白盒体验

1. 上传点子或 PRD
2. 确认产品方案
3. 生成与预览
4. 部署与上线

用户进度统一显示为 `第 N 步，共 4 步`，不再显示八阶段编号、M1A 等内部代号。

## 4. 目标用户与核心任务

### 4.1 目标用户

- 有产品或业务想法，但不会写代码；
- 能描述用户、场景和期望结果；
- 愿意对产品范围、体验、费用和风险做决定；
- 希望直接获得可体验、可上线的产品，而不是一份代码示例。

### 4.2 用户核心任务（JTBD）

当我有一个产品想法时，我希望用自然语言把它交给工厂；工厂帮我补全需求、给出可理解的实现方案、自动生成并测试产品，让我通过真实预览持续确认，最终获得上线地址和完整交付物，而不需要学习开发流程。

## 5. 产品原则

1. **产品语言优先**：主界面不出现代码、框架、API、Token、Git、Runtime、Queue 等词。
2. **决策优先**：只有当问题影响产品范围、用户体验、费用、数据安全或外部权限时，才要求用户确认。
3. **单一推荐方案**：工厂默认给出一个推荐方案，并说明理由、代价和限制；不让用户在多个技术栈之间选择。
4. **结果可见**：每一步都要说明已经得到什么、现在需要做什么、确认后会发生什么。
5. **渐进披露**：先展示产品结论，需要时再展开实现说明和技术证据。
6. **真实体验代替技术汇报**：优先让用户操作预览，而不是阅读开发日志。
7. **允许后悔**：关键确认点应说明修改影响，并保留可恢复版本。

## 6. 四阶段详细需求

### 6.1 第一阶段：上传点子或 PRD

**用户心智：把想法说清楚。**

#### 输入

- 一句话想法；
- 一段自然语言描述；
- 已有 PRD、文档或参考资料；
- 可选的参考产品或图片。

#### 工厂输出

- 产品目标；
- 目标用户；
- 核心使用场景；
- 首版必须完成的功能；
- 暂不实现的内容；
- 仍需用户回答的关键问题。

#### 用户操作

- 补充信息；
- 修改理解偏差；
- 确认“这就是我要做的产品”。

#### 页面要求

- 页面主标题使用“告诉我你想做什么”；
- 支持文字输入和文件上传；
- 缺失信息以一次一个问题的方式追问；
- 不展示需求解析链路、Agent 名称或内部任务。

### 6.2 第二阶段：确认产品方案

**用户心智：确认做什么、怎么实现、代价是什么。**

技术方案属于白盒，但必须用非技术用户能判断的语言表达。

#### 方案必须包含

1. **产品范围**：首版包含什么、不包含什么；
2. **用户流程**：用户从进入产品到完成目标会经历什么；
3. **页面与功能**：会生成哪些页面，每个页面解决什么问题；
4. **AI 的作用**：AI 在哪里参与、需要什么输入、失败时如何处理；
5. **数据说明**：保存哪些数据、保存在哪里、用户能否删除或导出；
6. **外部服务**：是否需要域名、短信、支付、地图、邮箱或其他账号授权；
7. **费用预估**：上线前固定成本、使用量增长后可能产生的成本及触发条件；
8. **风险与取舍**：当前方案的限制、替代方式和工厂的推荐理由；
9. **交付内容**：预览、线上地址、源代码、测试结果和使用说明；
10. **未来扩展**：首版上线后可以怎样继续增加能力。

#### 表达示例

| 不应直接展示 | 应展示为 |
| --- | --- |
| PostgreSQL + Prisma | 产品会安全保存账号和内容数据，并支持后续导出 |
| 调用第三方 LLM API | 该功能需要 AI 服务；工厂会先使用推荐配置，并展示预计费用 |
| OAuth / API Key | 发布前需要你授权对应服务，授权信息不会展示给其他用户 |
| Redis Queue | 耗时任务会在后台继续运行，完成后通知你 |
| S3 Object Storage | 上传的图片和文件会保存到独立文件空间 |

用户可展开“为什么这样做”查看进一步解释；框架名、数据库表、接口结构等进入“实现说明”，不占据主流程。

#### 用户操作

- 确认方案；
- 对某一项提出修改；
- 接受或拒绝费用、权限和风险项；
- 确认开始生成产品。

### 6.3 第三阶段：生成与预览

**用户心智：看着产品长出来，并在真实体验中修改。**

#### 主界面展示

- 当前正在完成的产品成果，例如“正在生成登录后的项目首页”；
- 已完成的页面或能力；
- 预计下一项成果；
- 可进入的真实预览；
- 质量检查结果；
- 需要用户决定的问题。

#### 主界面不展示

- 文件修改列表；
- 代码 diff；
- 命令行输出；
- 模型名称和 Token 消耗；
- 测试框架、构建日志和内部重试；
- 八阶段中的自动开发、测试、额度调度等独立步骤。

#### 反馈方式

用户可以直接描述：

- “这里不是我想要的”；
- “这个按钮换个位置”；
- “还需要一个功能”；
- “我不理解这段内容”；
- “恢复到上一个版本”。

工厂需要判断反馈属于：

- 当前方案内的修改：直接处理；
- 产品范围变化：说明影响并请求确认；
- 需要新增费用或权限：先解释并确认；
- 无法实现：说明原因并给出替代方案。

### 6.4 第四阶段：部署与上线

**用户心智：把产品交到手里。**

#### 发布前确认

- 发布到哪里；
- 使用默认地址还是自有域名；
- 需要用户提供哪些账号或授权；
- 预计固定费用和使用费用；
- 数据与隐私设置；
- 上线检查是否通过。

#### 发布后交付

- 可访问的线上地址；
- 管理入口；
- 产品使用说明；
- 测试与质量检查摘要；
- 完整源代码和交付包；
- 当前版本与恢复点；
- 后续修改和运营入口。

运行监控、备份和异常恢复继续由工厂在后台处理。只有当问题影响用户或需要用户决策时，才在前台以“发生了什么—有什么影响—建议怎么做”展示。

## 7. 四阶段与内部八阶段映射

后台保留现有状态机和接口，前台增加用户阶段聚合层。

| 用户可见阶段 | 对应内部阶段 | 前台转换规则 |
| --- | --- | --- |
| 1. 上传点子或 PRD | M1A 需求与方案（需求部分） | 只展示需求理解、追问和范围确认 |
| 2. 确认产品方案 | M1A 方案部分 + M1B 产品地图 | 转换为产品范围、流程、页面、费用、风险和交付说明 |
| 3. 生成与预览 | M1C 自动开发 + M1D 测试预览 + M2A 额度与模型 | 合并为成果进度、真实预览和质量检查；仅在必要时展示 AI 费用或授权 |
| 4. 部署与上线 | M2B 授权部署 + M2C 完整交付 + M3/M4 稳定运营 | 合并为发布确认、上线结果和持续运行状态 |

### 7.1 阶段状态

每个用户阶段只使用以下状态：

- 未开始；
- 正在进行；
- 等你确认；
- 已完成；
- 需要处理。

内部的排队、运行、重试、失败类型等状态由聚合层翻译成用户可理解的说明。

## 8. 信息架构与页面改造

### 8.1 左侧导航

仅保留四个阶段：

1. 上传点子或 PRD
2. 确认产品方案
3. 生成与预览
4. 部署与上线

顶部进度改为四阶段进度，例如：

- `产品进度 25%`
- `正在进行第 1 步，共 4 步`

移除 M1A、M1B、M2A、M3/M4 等内部标识。

### 8.2 主工作区

每个阶段保持统一结构：

1. **当前目标**：这一阶段要得到什么；
2. **已经完成**：工厂产出的可验证结果；
3. **需要你确认**：用户真正需要做的决定；
4. **接下来**：确认后工厂会继续做什么；
5. **实现说明**：默认收起的二级信息。

### 8.3 项目首页

项目卡片显示：

- 产品名称；
- 一句话说明；
- 当前四阶段状态；
- 最近更新；
- 继续创建按钮。

项目卡片 hover 时展示删除入口，删除项目时必须弹窗二次确认，并明确删除影响。登录首页保持不变。

## 10. 功能需求优先级

### P0：本次 Web 改版必须完成

- 将八阶段主导航改为四阶段用户导航；
- 建立四阶段与八阶段的前端映射，不改坏后端状态机；

- 将自动开发、测试、额度调度合并进“生成与预览”；
- 将授权、部署、交付和运营合并进“部署与上线”；
- 将技术日志、代码与配置收进默认折叠的“实现说明”；

### P1：后续增强

- 在预览页面直接标注需要修改的位置；
- 为费用、数据和权限提供更直观的影响说明；
- 提供面向技术接手人的完整实现报告；
- 上线后提供产品语言的运行健康报告。

## 11. 本期不做

- 不在普通用户主界面增加代码编辑器或终端；
- 不要求用户选择框架、数据库、模型供应商或部署区域；
- 不把八阶段继续作为主导航；
- 不展示原始模型调用、Token 流水或运行日志；
- 不提供常驻的“黑盒模式”切换；
- 不修改登录首页的视觉和交互。

## 12. 验收标准

### 12.1 理解度

- 非技术测试用户进入项目后 10 秒内能说出当前处于哪一步；
- 用户能说清楚产品方案包含什么、成本来自哪里、需要提供什么权限；
- 主流程中不出现 M1A、API、Token、Git、Runtime、Queue 等未解释技术词；
- 用户无需理解代码即可完成从想法到上线的完整流程。

### 12.2 界面与交互

- 左侧仅展示四阶段，进度按四阶段计算；
- 当前阶段、已完成阶段和待确认阶段有明确视觉区分；
- 每个确认按钮都说明确认后的结果；
- 技术信息默认折叠，但专业人员仍可通过“实现说明”追溯；
- 桌面端和移动端均可完成核心操作；
- 项目删除必须经过确认弹窗；
- 登录首页无视觉或功能回归。

### 12.3 流程与兼容性

- 现有八阶段后台任务仍能按原顺序运行；
- 刷新页面后四阶段状态与内部任务状态一致；
- 内部任务失败时，前台展示影响、建议和可执行动作；
- 用户修改范围后，能重新确认方案并继续生成；
- 完成发布后能够访问线上地址并下载交付物。

## 13. 核心指标

- 四阶段流程自主完成率；
- “确认产品方案”一次理解并通过的比例；
- 从创建项目到获得首次可用预览的时间；
- 用户因技术词或技术配置请求人工帮助的次数；
- 预览反馈成功转化为产品修改的比例；
- 从预览完成到成功上线的转化率。

## 14. Web 改造建议顺序

1. 新增四阶段展示模型及八阶段映射；
2. 改造侧边栏、进度卡和阶段标题；
3. 重构“确认产品方案”的内容结构；
4. 合并“生成与预览”相关技术页面；
5. 合并“部署与上线”相关技术页面；
6. 将技术证据迁移到“实现说明”；
7. 补齐四阶段状态、异常和刷新恢复测试；
8. 使用完整测试项目跑通创建、确认、预览、发布和交付。

## 15. 测试项目：每日三件事

为了验证非技术用户能否独立跑完整个流程，使用以下测试项目：

> 我想做一个简单的每日计划产品。用户每天写下最重要的三件事，完成后可以打勾，晚上看到当天完成情况，并能回顾最近七天。界面要简单、适合手机使用，不需要社交功能。

### 预期流程

1. 工厂补全目标用户、核心场景和首版范围；
2. 用户确认页面、流程、数据保存方式、费用和交付内容；
3. 工厂生成登录后首页、每日任务、完成状态和七天回顾；
4. 用户进入真实预览并提出至少一次界面修改；
5. 工厂完成质量检查；
6. 用户确认发布并获得线上地址与交付包。

### 测试通过条件

- 用户全程不需要选择技术栈；
- 用户能理解方案中的数据、费用和限制；
- 四阶段进度正确推进；
- 修改后预览能更新且可恢复上一版本；
- 发布成功后线上产品可正常新增、勾选和回顾任务；
- 出错时页面给出用户能执行的解决办法，而不是原始技术日志。
